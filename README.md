# 움직이는 쓰레기통 (자율주행 캐치 로봇)

낙하하는 쓰레기를 카메라로 인식하고, 낙하 궤적을 예측해 로봇이 물체 아래로 이동하여 받아내는
3륜 홀로노믹 자율주행 로봇.

## 목표 스펙

| 항목 | 값 |
|---|---|
| 투척 높이 | 2.0 m |
| 유효 캐치 반경 | **40 cm (보증)** / 48 cm (μ=0.5 계산) |
| 모터 | FIT0186 (251 RPM, 18 kgf·cm, 43.8:1) ×3 |
| 검출 모델 | YOLO11n (커스텀 학습 → Hailo `.hef`) |
| 통 입구 지름 | **30 cm** (깊이 20 cm) |
| 목표 성공률 | 70% 이상 |
| 대상 클래스 | pet_bottle / can / paper_cup (**50~100 g으로 채워 사용, 100 g 권장**) |
| 카메라 / 렌즈 | HQ Camera (IMX477) + 6 mm 광각 (F1.2) |
| 인식 주기 / 제어 주기 | 40 fps / 1 kHz |

**유효 캐치 반경 = 로봇 이동거리(33 cm) + 통 입구 반경(15 cm)** 이다. 물체는 로봇 중심이
아니라 통 안에만 들어오면 되기 때문이다
([physics.md 6장](docs/physics.md#6-통-입구-크기--설계의-지렛대)).

> 병목은 모터가 아니라 **바닥 마찰**이다. 모터는 16.3 m/s²를 낼 수 있는데 마찰 한계가
> 2.45 m/s²다. 게다가 3륜 옴니는 힘 분배 제약 때문에 견인 한계가 `0.5·μ·g`로 단순 계산의
> 절반이다 ([physics.md 2장](docs/physics.md#2-3륜-옴니의-힘-분배)).
>
> `a = 0.5μg`에 질량이 없다는 것은 **통을 크게 만드는 비용이 사실상 0**이라는 뜻이다.

**비목표:** 여러 물체 동시 추적, 장애물 회피, 로봇 회전(θ) 제어, 캐치 성공/실패 자동 판정,
통 비우기.

## 동작 원리

매 프레임 아래를 반복한다. 별도의 "확정 단계"나 "재보정 루프"가 없는
**단일 연속 추정 루프**다.

```
                     ┌─────────── 파이5 (Python, 40 Hz) ───────────┐
                     │                                             │
  [카메라] ─프레임──▶ │ vision      YOLO11n(ROI) → 픽셀 → body 좌표  │
                     │    ↓                                        │
                     │ frames      body → world 변환 (오도메트리)   │
                     │    ↓                                        │
                     │ estimator   포물선 칼만필터 (world frame)    │
                     │    ↓                                        │
                     │ trajectory  착지점·착지시각 예측             │
                     │    ↓                                        │
                     │ control     목표 속도 (body frame) + TTL     │
                     └──────────────────┬──────────────────────────┘
                                        │ USB CDC
                       속도명령 ▼       ▲ 오도메트리 (100 Hz)
                     ┌──────────────────┴──────────────────────────┐
                     │            피코 (C, 1 kHz)                   │
                     │  엔코더(PIO) → 순기구학 → 칼만 → 오도메트리   │
                     │  목표속도 → 역기구학 → PID+FF → PWM          │
                     └──────────────────┬──────────────────────────┘
                                        ▼
                                  [모터 ×3 / 옴니휠 ×3]
```

**역할 분담:** 파이5는 "어디로 얼마나 빨리 가야 하는가"를 결정하고, 피코는 "그 속도를 정확히
내는 것"만 한다. 피코는 궤적도 착지점도 모른다.

z(높이)는 **bbox 폭**과 실물 치수의 비로 추정한다. 단안 카메라에서 크기 정보가 유일한
스케일 소스이기 때문이다. 높이가 아니라 폭을 쓰는 이유는 HQ 카메라가 롤링 셔터라
행 방향(높이)에만 왜곡이 생기기 때문이다 ([physics.md 7.1장](docs/physics.md#71--롤링-셔터다)).

## 코드 구조

```
pi5/     라즈베리파이5 (Python) — 비전, 궤적 추정, 목표 속도 산출
pico/    라즈베리파이 피코 (C)  — 엔코더, 기구학, 오도메트리, PID 모터 제어
docs/    설계 문서
tests/   단위 테스트 + 시뮬레이터 기반 성공률 회귀 테스트
```

| 보드 | 언어 | 이유 |
|---|---|---|
| 파이5 | Python | Hailo SDK가 Python 우선. 무거운 연산은 NPU가 처리 |
| 피코 | C (Pico SDK) | PIO 엔코더 타이밍 정밀도, PID 루프 지터 최소화 |

## 개발 로드맵

**하드웨어가 없는 지금, 순서를 잘 잡으면 부품이 오기 전에 알고리즘을 완성할 수 있다.**

### Phase 0 — 시뮬레이터와 테스트 ★최우선 (하드웨어 불필요)

1. `tests/` 구축: 기구학 왕복, 좌표 변환, 착지 예측, 프로토콜 인코딩/디코딩
2. `pi5/sim/world.py`: 물체 낙하(중력 + 항력) + 로봇 운동(견인 한계 `0.5μg`) 모델
3. `pi5/sim/fake_camera.py`: 물체 world 좌표 → body 변환 → 핀홀 투영 → bbox 합성 + 노이즈 주입.
   **YOLO를 흉내내는 게 아니라 YOLO의 출력(`Detection`)을 흉내낸다.**
   SEARCH/TRACK에 따라 σ_w를 다르게 준다(6.3 px / 2 px)
4. `pi5/sim/fake_link.py`: 피코 모델 (속도 명령 → 가감속 → 오도메트리)
5. `main.py`가 진짜/가짜 구현을 **의존성 주입**으로 갈아끼울 수 있게 한다

**완료 기준:** `python -m pi5.main --sim`이 끝까지 돌고 캐치 성공/실패를 출력한다.

### Phase 1 — 알고리즘 검증 (하드웨어 불필요)

1. 투척 위치·속도를 무작위로 1000회 돌려 캐치 성공률 측정
2. 노이즈 파라미터를 [physics.md](docs/physics.md)의 계산값으로 설정
3. **목표(2 m 낙하, 유효 반경 40 cm, 성공률 70%)를 시뮬레이터에서 먼저 달성한다**
4. 실패 케이스 분석 → 칼만 파라미터·제어 게인 조정
5. `tests/test_catch_rate.py`로 회귀 방지

**여기서 안 되면 실물에서도 안 된다. 부품 사기 전에 확인한다.**

### Phase 2 — 부품 구매와 조립

[hardware.md 8장](docs/hardware.md#8-부품-체크리스트) 확정 → 구매 → 섀시 제작 → 배선 →
핀 번호 확정

### Phase 3 — 피코 브링업

빌드 → 엔코더 → 모터 개루프 → 속도 폐루프 → 3륜 합성 → 오도메트리 검증 →
**가속도 실측** → 통신 왕복.
상세 절차는 [pico-control.md 10장](docs/pico-control.md#10-브링업-절차).

> 7단계의 **마찰계수 μ 실측**이 중요하다. 캐치 반경이 여기서 확정된다 (μ=0.4면 유효 41 cm,
> μ=0.7이면 56 cm). 보증치 40 cm는 최악을 가정한 값이라 실측 후 상향할 수 있다.

### Phase 4 — 비전 파이프라인

캘리브레이션 → 촬영 → 라벨링 → YOLO11n 학습 → **σ_w 측정** → Hailo 컴파일 →
σ_w 재측정 → ROI 추적 통합.
상세 절차는 [vision-pipeline.md 9장](docs/vision-pipeline.md#9-작업-순서).

> **합격 기준은 mAP가 아니라 σ_w ≤ 2 px다.** bbox 폭 오차가 그대로 거리 오차가 되기
> 때문이다. 여기서 못 맞추면 되돌아간다
> ([vision-pipeline.md 7장](docs/vision-pipeline.md#7-검증-지표)).

낙하 영상은 학습 데이터이자 **클래스별 `g_eff` 피팅** 자료로 함께 쓴다.

### Phase 5 — 통합

시뮬레이터를 실물로 교체하고 Phase 1의 성공률을 재측정한다. 차이가 나면 시뮬레이터의
노이즈 모델을 실측값으로 보정한다 — **시뮬레이터는 계속 유지한다.**

### Phase 6 — 튜닝

성공률 목표 달성, 실패 케이스 분석, 파라미터 최적화.

## 현재 상태

**하드웨어 미구매 — 설계 단계.**

기존 2단계 설계(확정 → 속도 3프레임 측정 → 예측 → 재보정 루프)는 3프레임 차분으로 구한
vz의 오차가 1.8 m/s에 달해 원리적으로 동작하지 않는다는 것이 확인되어
([physics.md 8장](docs/physics.md#8-속도-추정-오차--설계를-바꾼-계산)),
**연속 추정 루프로 재설계**했다.

현재 코드는 이전 설계를 따르고 있어 재작성이 필요하다. 변경 범위는
[pi5-algorithm.md 9장](docs/pi5-algorithm.md#9-현재-코드-대비-변경점) ·
[pico-control.md 8장](docs/pico-control.md#8-현재-코드-대비-변경점)에 파일별로 정리되어 있다.
