# 비전 파이프라인 — 데이터셋부터 추론까지

쓰레기 사진 촬영 → 라벨링 → YOLO11n 학습 → Hailo 컴파일 → 추론까지의 전 과정.

이 파이프라인의 출력은 `Detection(class_name, bbox, confidence)` 하나이고,
그 bbox가 [궤적 계산](pi5-algorithm.md)의 유일한 입력이다.

관련 문서: [파이5 알고리즘](pi5-algorithm.md) · [물리 계산](physics.md) · [하드웨어](hardware.md)

---

## 1. 이 시스템에서 YOLO의 역할은 특이하다

일반적인 객체 검출은 **"거기에 있다"**만 맞으면 된다. 이 시스템은 다르다.

```
z = f_px × W_real / w_px          ← bbox 폭이 곧 거리다
```

**bbox 폭 오차가 그대로 z 오차가 되고, z 오차가 착지 예측 전체를 좌우한다.**
따라서 우리가 관리해야 할 지표는 mAP가 아니라 **bbox 폭의 픽셀 오차 σ_w**다.

| 일반 검출 | 이 시스템 |
|---|---|
| mAP@0.5 이면 충분 | **σ_w (bbox 폭 오차, px)** 가 핵심 |
| 클래스 혼동 = 라벨만 틀림 | 클래스 혼동 = **잘못된 실물 치수 → z가 틀림** |
| 느슨한 bbox 허용 | 느슨한 bbox = 거리 오차 |

`σ_w = 2 px` 가정 위에 [physics.md](physics.md)의 모든 정확도 계산이 서 있다
([physics.md 9장](physics.md#9-확정된-설계-상수와-미검증-가정)).
**이 파이프라인의 목표는 σ_w를 2 px 이하로 만드는 것이다.**

### 클래스 혼동의 비용

| 혼동 | 실물 치수 차이 | z 오차 |
|---|---|---|
| can ↔ pet_bottle | 66 mm ↔ 65 mm | 1.5% (무해) |
| can ↔ paper_cup | 66 mm ↔ 80 mm | **21% (치명적)** |

can과 pet_bottle을 헷갈리는 것은 괜찮지만, **paper_cup과 헷갈리면 z가 21% 틀린다.**
paper_cup을 클래스에서 빼면 이 위험이 사라진다 (7장).

## 2. ⚠ 추론 해상도가 z 정확도를 2배 이상 좌우한다

**가장 중요한 설계 결정이다.**

YOLO11n의 기본 입력은 640×640이다. 원본 1456×1088을 그대로 리사이즈하면 스케일이
640/1456 = 0.44로 줄어들고, **bbox도 같이 줄어든다.**

| 추론 입력 | 2 m에서 캔 bbox | 프레임당 σ_z | 배율 |
|---|---|---|---|
| 640 리사이즈 (전체 프레임) | **11 px** | 35 cm | 2.3배 나쁨 |
| **640 ROI 크롭 (네이티브 픽셀)** | **26 px** | **15.3 cm** | **기준** |

**전체 프레임을 640으로 줄이면 물체가 11 px까지 작아진다.** 거리 오차가 2.3배로 늘 뿐
아니라, **YOLO가 11 px 물체를 안정적으로 검출하지 못할 위험**이 더 크다
(보통 8~10 px 이하에서 검출률이 급락한다).

### → 2단계 추론 전략

```
[탐색 단계]  전체 프레임 → 640 리사이즈 → 추론
             목적: "어디에 있는지"만 찾기. 정밀도는 필요 없다.

[추적 단계]  칼만필터가 예측한 이미지 위치 중심으로
             네이티브 해상도에서 640×640 크롭 → 추론
             목적: 정밀한 bbox. 스케일 손실이 없다.
```

**탐색은 위치만 찾고, 정밀도는 추적이 담당한다.** 첫 프레임의 z는 부정확해도(σ_z ≈ 16 cm)
칼만필터가 어차피 큰 불확실성으로 시작하므로 문제되지 않는다. 2~3프레임 안에 ROI 추적으로
넘어가면서 정밀도가 확보된다.

**부수 효과: 추론 비용이 동일하다.** 두 단계 모두 입력이 640×640이라 Hailo 부하가 같다.

### ROI 크기 검증

640×640 ROI가 낙하 전 구간에서 충분한지 확인했다 (수평 속도 1 m/s 가정, 60 fps):

| z | 물체 이미지 속도 | 프레임당 이동 (60 fps) | 물체 폭 | ROI 여유 |
|---|---|---|---|---|
| 2.0 m | 396 px/s | 7 px | 26 px | 충분 |
| 1.0 m | 792 px/s | 13 px | 52 px | 충분 |
| 0.5 m | 1584 px/s | 26 px | 104 px | 충분 |
| 0.11 m | 7200 px/s | 120 px | 474 px | 프레임 이탈 시점 |

(중심부 기준. 어안이라 가장자리에서는 국소 배율이 작아 이동·크기가 더 줄어든다)

물체가 커지고 빨라져도 640 안에 들어온다. 카메라가 통 입구 가장자리에 있어
**z ≈ 0.11 m에서 물체가 프레임을 벗어나지만**, 그 시점이면 예측이 이미 수렴한 뒤라
칼만필터가 외삽한다 ([physics.md 6장](physics.md#카메라를-입구에-두는-대가--오프셋)).

**ROI를 놓쳤을 때:** 크롭 안에서 검출이 없으면 다음 프레임은 전체 프레임 탐색으로 되돌린다.
칼만필터는 유지한 채로 재획득한다.

## 3. 데이터셋 수집

### 왜 커스텀 학습이 필요한가

COCO 사전학습 모델에도 `bottle`, `cup`이 있지만 쓸 수 없다.

- **시점이 다르다.** 우리는 **아래에서 위를 본다.** COCO는 대부분 눈높이 측면 촬영이다
- **배경이 천장이다.** 형광등, 파이프, 천장 타일 — COCO에 거의 없는 배경
- **자세가 임의다.** 낙하 중 회전하며 떨어진다
- **모션 블러가 있다.** 6 m/s로 움직이는 물체 (글로벌 셔터라 왜곡은 없지만 블러는 남는다)
- **클래스 정의가 다르다.** 우리는 `can`이 필요한데 COCO에는 없다

### 촬영 조건

**실제 추론 조건과 같아야 한다.** 이게 원칙이다.

- 카메라를 **실제 장착 위치**(통 입구 림, 수직 상방)에 두고 촬영
- **실제 낙하 영상**을 찍어 프레임을 추출하는 것이 가장 효율적
  - 1초 영상 @ 60 fps = 60장
  - 노출·조명도 실제 설정 그대로 (0.84 ms, LED/스트로브 포함)
- 정지 물체도 일부 촬영 — **거리별로 찍어두면 z 추정 검증에 그대로 쓸 수 있다**

### 다양성 축

연속 프레임은 서로 거의 같아서 장수만 늘어나고 실질 다양성이 안 늘어난다.
**투척 횟수를 늘리는 것이 프레임을 더 뽑는 것보다 중요하다.**

| 축 | 범위 |
|---|---|
| 거리 z | 0.3 ~ 2.5 m (낙하 전 구간이 자연히 커버) |
| 자세 | 세로/가로/기울어짐 — 회전하며 떨어지므로 자연히 확보 |
| 배경 | 천장 3~5종 (강의실, 복도, 실험실 등) |
| 조명 | 형광등 / LED 보조광 / 혼합 |
| 물체 개체 | 클래스당 3~5종 (브랜드·색상 다르게) |

### 목표 수량

| 항목 | 수량 |
|---|---|
| 투척 영상 | **100회 이상** (클래스당 30~40회) |
| 회당 추출 프레임 | 10~15장 (낙하 구간 균등 샘플) |
| 낙하 프레임 합계 | 1000 ~ 1500장 |
| 정지 물체 (거리별) | 300장 |
| **합계** | **1300 ~ 1800장** |

### ⚠ 분할은 프레임이 아니라 **영상 단위**로

같은 영상에서 뽑은 프레임은 서로 거의 동일하다. 프레임 단위로 무작위 분할하면 train과 val에
사실상 같은 이미지가 들어가 **검증 점수가 부풀려지고 과적합을 못 잡는다.**

```
train / val / test = 70 / 20 / 10   ← 영상(투척 회차) 단위로 분할
test는 가능하면 별도 촬영 세션으로 확보
```

## 4. 라벨링

### 도구와 형식

- 도구: Roboflow / CVAT / LabelImg 중 택1
- 형식: **YOLO txt** — `class_id cx cy w h` (0~1 정규화)
- 클래스: `0 can`, `1 pet_bottle`, `2 paper_cup`

### ⚠ 라벨 품질이 곧 z 정확도다

**라벨링이 엉성하면 σ_w가 커지고, σ_z가 그대로 비례해서 나빠진다.**
σ_w가 2 px → 5 px가 되면 프레임당 σ_z가 15.3 cm → 38 cm가 되고, 피팅 후 착지 오차도
2.5배로 늘어난다.

규칙:

1. **물체 외곽에 타이트하게.** 여백을 두지 않는다
2. **모션 블러 처리를 일관되게.** 블러 꼬리를 포함할지 말지 정하고 **끝까지 같은 기준**을
   적용한다. 일관된 편향은 캘리브레이션으로 흡수할 수 있지만, 들쭉날쭉한 오차는 못 없앤다
3. **가려짐(occlusion)이 있으면 제외.** 통 벽에 반쯤 가려진 프레임은 bbox 폭이 의미가 없다
4. **여러 명이 라벨링하면 먼저 기준을 맞춘다.** 같은 이미지 20장을 각자 라벨링해서
   폭 차이를 비교한다 — 이게 σ_w의 하한이다

> **일관성 > 절대 정확도.** 모두가 3 px씩 크게 그렸다면 `OBJECT_SIZE_M`을 그만큼 키워
> 보정할 수 있다. 사람마다 다르게 그렸다면 방법이 없다.

## 5. 학습 (YOLO11n)

### 왜 YOLO11n인가

- **n(nano)**: Hailo-8L에서 60 fps를 노려볼 수 있다. 프레임 예산이 16.7 ms이고 추론은
  10 ms 이내여야 한다 ([physics.md 7.4장](physics.md#74-프레임레이트와-처리-예산))
- 클래스 3개, 물체가 단순해서 큰 모델이 필요 없다
- 정확한 bbox 회귀가 목표인데, 이건 모델 크기보다 **데이터 품질**에 더 좌우된다

### 설정

```yaml
# dataset.yaml
path: ./dataset
train: images/train
val: images/val
names:
  0: can
  1: pet_bottle
  2: paper_cup
```

```python
from ultralytics import YOLO
model = YOLO("yolo11n.pt")          # COCO 사전학습 가중치에서 시작
model.train(
    data="dataset.yaml",
    imgsz=640,                       # ROI 크롭 크기와 일치시킨다 (2장)
    epochs=100,
    batch=16,
    patience=20,
)
```

**`imgsz=640`을 ROI 크롭 크기와 일치시키는 것이 중요하다.** 학습 때 본 물체 크기 분포와
추론 때 들어오는 분포가 같아야 bbox 회귀가 정확하다.

### 증강 주의사항

기본 증강은 대체로 도움이 되지만 두 가지는 조정한다.

- **좌우/상하 반전은 안전하다** (물체가 대칭이고 방향 의미가 없다)
- **과도한 scale 증강은 피한다.** bbox 크기가 곧 신호인데, 학습 분포를 너무 넓히면
  회귀 정밀도가 떨어질 수 있다. 실제 z 범위(0.3~2.5 m)에 해당하는 크기 범위면 충분하다
- **mosaic은 마지막 10 에폭에서 끈다** (`close_mosaic=10`, 기본값). 실제 추론에는
  모자이크가 없으므로 마무리는 실제 분포로 한다

## 6. Hailo 컴파일

```
yolo11n.pt  ──export──▶  ONNX  ──Hailo DFC──▶  .hef
                                  │
                          INT8 양자화 + calibration
```

### 절차

1. **ONNX 내보내기** — `model.export(format="onnx", imgsz=640, opset=...)`
2. **Hailo Dataflow Compiler**로 파싱 → 최적화 → 컴파일
3. **INT8 양자화 캘리브레이션** — 학습 데이터에서 **수백 장**을 캘리브레이션 세트로 제공.
   실제 추론 분포와 같아야 하므로 **ROI 크롭 이미지를 쓴다**
4. `.hef` 산출 → `config.YOLO_MODEL_PATH`에 경로 지정

### ⚠ 확인이 필요한 것

- **Hailo Model Zoo의 yolo11n 지원 여부를 먼저 확인한다.** 지원이 없으면 yolov8n으로
  대체한다 (이 문서의 나머지는 그대로 유효하다)
- **INT8 양자화가 bbox 정밀도를 떨어뜨릴 수 있다.** 양자화 전후로 σ_w를 비교해서
  열화 폭을 반드시 측정한다. 이게 이 단계의 핵심 검증 항목이다

## 7. 검증 지표

**mAP만 보면 안 된다.** 이 시스템에 필요한 지표는 따로 있다.

| 지표 | 목표 | 측정 방법 |
|---|---|---|
| **σ_w (bbox 폭 오차)** | **≤ 2 px** | 정지 물체를 알려진 거리에서 촬영 → 예측 폭의 표준편차 |
| σ_z / z (상대 거리 오차) | ≤ 3.5% | 위와 동일, `z = f·W/w`로 환산 |
| 추론 지연 (60 fps 전 프레임) | ≤ 16.7 ms | 초과 시 30 fps 격프레임 ([physics.md 7.4장](physics.md#74-프레임레이트와-처리-예산)) |
| 검출률 (recall) | ≥ 95% | 낙하 test 영상의 프레임별 |
| paper_cup ↔ can 혼동률 | ≤ 2% | 혼동 행렬 |

**σ_w 측정이 이 파이프라인의 합격 기준이다.** 정지한 캔을 1 m, 1.5 m, 2 m, 2.5 m에서
각각 100프레임 촬영하고 예측 bbox 폭의 표준편차를 재면 된다. 이 값이 그대로
[physics.md](physics.md)의 σ_z 계산에 들어간다.

### 클래스 축소 판단

paper_cup은 세 가지가 동시에 불리하다.

- 항력이 가장 크다 (100 g에서도 중력의 12%, [physics.md 4장](physics.md#4-항력--포물선-모델이-양쪽-축에서-흔들린다))
- 실물 치수가 can/pet_bottle과 20% 달라 클래스 혼동 비용이 크다 (1장)
- 입이 열려 있어 자세에 따라 bbox 폭 변화가 크다

**can 1종으로 시작해 파이프라인을 끝까지 돌린 뒤 확장하는 것을 권장한다.**
데이터 수집·라벨링 부담이 1/3이 되고, 클래스 혼동 위험이 사라진다.

## 8. 소프트웨어 인터페이스

`catcher/vision.py`가 제공하는 계약이다. 아래 두 함수만 [main 루프](pi5-algorithm.md#4-메인-루프)가 쓴다.

```python
@dataclass
class Detection:
    class_name: str
    bbox: tuple[float, float, float, float]   # cx, cy, w, h  (원본 1456×1088 픽셀 기준)
    confidence: float

def detect_full(frame) -> Detection | None:
    """전체 프레임 640 리사이즈 추론. 탐색 단계용."""

def detect_roi(frame, center_px: tuple[float, float]) -> Detection | None:
    """center_px 중심 640×640 네이티브 크롭 추론. 추적 단계용."""
```

**두 함수 모두 bbox를 원본 1456×1088 좌표계로 되돌려 반환한다.** ROI 오프셋과 리사이즈
스케일 역변환은 `vision.py` 안에서 끝내고, 바깥에서는 좌표계를 하나만 본다.

```
detect_full:  bbox_원본 = bbox_640 × (1456/640)
detect_roi :  bbox_원본 = bbox_640 + (roi_x0, roi_y0)      ← 스케일 없음
```

전처리(letterbox, 정규화)와 후처리(NMS)도 이 안에 둔다.
`main.py`는 `Detection`만 받는다.

## 9. 작업 순서

이 순서대로 하면 앞 단계 결과로 뒷 단계를 검증할 수 있다.

1. **어안 카메라 캘리브레이션** — `cv2.fisheye.calibrate`로 `f_px`, 주점, 왜곡계수 확보.
   번들 렌즈는 대각 140° 어안이라 **일반 핀홀 캘리브레이션으로는 안 된다**
   ([physics.md 7.2장](physics.md#72--이-렌즈는-핀홀이-아니다))
2. **정지 물체 촬영** — 거리별. 데이터셋 겸 σ_w 측정용 기준 세트
3. **낙하 영상 촬영** — 100회 이상, 배경·조명 다양화
4. **프레임 추출 + 라벨링** — 라벨 기준 먼저 합의
5. **YOLO11n 학습** — val에서 recall 확인
6. **σ_w 측정** (양자화 전) — 2번 세트로. **여기서 2 px를 못 맞추면 되돌아간다**
7. **Hailo 컴파일 + 양자화**
8. **σ_w 재측정** (양자화 후) — 열화 폭 확인
9. **추론 지연 측정** — 10 ms 예산 검증
10. **ROI 추적 통합** — `detect_roi` 연결, 재획득 동작 확인
