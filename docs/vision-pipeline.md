> ## ⚠ 이 문서의 전제가 2026-08-10에 바뀌었다
>
> 깊이 추정이 **bbox 크기비율 → 중력 기반 궤적 최소제곱**으로 전환됐다
> ([`../pi5/trajectory.py`](../pi5/trajectory.py), [`../algorithm.md`](../algorithm.md)).
> 그 결과 **bbox 폭은 아무 데도 안 쓴다.** 궤적 추정의 입력은 bbox **중심(u,v)** 뿐이다.
>
> | | 예전 (이 문서의 원래 전제) | 지금 |
> |---|---|---|
> | 깊이 스케일 | 물체 실물 치수 ÷ bbox 폭 | **중력 9.8 m/s²** |
> | 필요한 것 | 클래스별 실물 크기 등록 | 없음 |
> | 핵심 지표 | σ_w ≤ 2 px | **재투영 잔차 ≤ 4 px** |
> | 클래스 | can / pet_bottle / paper_cup | **`trash` 1개** |
>
> 아래 2~6장(해상도·데이터셋·라벨링·학습·컴파일)은 **그대로 유효하다** —
> 검출기를 잘 만드는 문제는 달라지지 않았다. 1장과 7장만 새 기준으로 고쳐 썼다.

## 1. 이 시스템에서 YOLO의 역할

일반적인 객체 검출은 **"거기에 있다"**만 맞으면 된다. 이 시스템도 이제 거의 그렇다.
필요한 건 **bbox 중심 하나**다.

```
관측 = (u, v)  →  중력 제약 하의 최소제곱  →  3D 궤적
```

깊이는 **중력이 준다.** 중력은 물체가 뭐든 항상 9.8 m/s²이므로, "이 궤적이 9.8의
중력으로 만들어지려면 거리가 얼마여야 하는가"를 역으로 풀면 스케일이 확정된다.
그래서 물체의 실제 크기를 알 필요가 없다.

### 왜 크기비율 방식을 버렸는가

두 가지가 결정적이었다.

- **회전.** 공중에서 물체가 돌면 보이는 폭이 최대 3배까지 흔들린다
  (500 ml 페트병: 세로 65 mm ↔ 가로 210 mm). bbox 폭이 거리인 방식에서는
  이게 그대로 거리 오차가 된다
- **클래스 혼동 비용.** 실물 치수가 20% 다른 클래스를 헷갈리면 z가 21% 틀렸다.
  이제 치수를 안 쓰므로 이 위험 자체가 없다 — 클래스도 `trash` 하나로 합쳤다

### 그래도 남는 요구사항

bbox **중심**의 정확도는 여전히 중요하다. 그게 궤적 피팅의 유일한 입력이다.
다만 성질이 다르다 — 폭 오차는 **거리에 직접** 들어가지만, 중심 오차는 여러 프레임에
걸친 최소제곱으로 **평균화되어 눌린다.** 관측을 늘릴수록 좋아진다는 뜻이고,
그래서 `MIN_OBSERVATIONS`와 `MIN_TIME_SPAN_S`가 정밀도의 손잡이가 됐다.

## 2. ⚠ 추론 해상도가 검출률을 좌우한다

**가장 중요한 설계 결정이다.**

YOLOv8n의 기본 입력은 640×640이다. 원본 1456×1088을 그대로 리사이즈하면 스케일이
640/1456 = 0.44로 줄어들고, **bbox도 같이 줄어든다.**

| 추론 입력 | 2 m에서 물체 bbox | 중심 좌표 정밀도 | 검출 위험 |
|---|---|---|---|
| 640 리사이즈 (전체 프레임) | **11 px** | 원본 환산 시 2.3배 나쁨 | **검출 실패 위험** |
| **640 ROI 크롭 (네이티브 픽셀)** | **26 px** | **기준** | 안전 |

**전체 프레임을 640으로 줄이면 물체가 11 px까지 작아진다.**
**YOLO가 11 px 물체를 안정적으로 검출하지 못할 위험**이 가장 크다
(보통 8~10 px 이하에서 검출률이 급락한다).

> 깊이가 중력에서 나오게 된 뒤로 **해상도가 거리 오차에 직접 들어가지는 않는다.**
> 하지만 리사이즈된 좌표를 원본으로 되돌리면 중심 오차도 2.3배로 커지고,
> 그게 재투영 잔차에 그대로 나타난다. 무엇보다 **검출을 놓치면 관측 수가 줄어
> 피팅 자체가 나빠진다** — `MIN_OBSERVATIONS = 4`를 못 채우면 그 투척은 실패다.

### → 2단계 추론 전략

```
[탐색 단계]  전체 프레임 → 640 리사이즈 → 추론
             목적: "어디에 있는지"만 찾기. 정밀도는 필요 없다.

[추적 단계]  칼만필터가 예측한 이미지 위치 중심으로
             네이티브 해상도에서 640×640 크롭 → 추론
             목적: 정밀한 bbox. 스케일 손실이 없다.
```

**탐색은 위치만 찾고, 정밀도는 추적이 담당한다.** 첫 프레임의 z는 부정확해도(σ_z ≈ 16 cm)
칼만필터가 어차피 큰 불확실성으로 시작하므로 문제되지 않는다. 2~3프레임 안에 ROI 추적으로
넘어가면서 정밀도가 확보된다.

**부수 효과: 추론 비용이 동일하다.** 두 단계 모두 입력이 640×640이라 Hailo 부하가 같다.

### ROI 크기 검증

640×640 ROI가 낙하 전 구간에서 충분한지 확인했다 (수평 속도 1 m/s 가정, 60 fps):

| z | 물체 이미지 속도 | 프레임당 이동 (60 fps) | 물체 폭 | ROI 여유 |
|---|---|---|---|---|
| 2.0 m | 396 px/s | 7 px | 26 px | 충분 |
| 1.0 m | 792 px/s | 13 px | 52 px | 충분 |
| 0.5 m | 1584 px/s | 26 px | 104 px | 충분 |
| 0.11 m | 7200 px/s | 120 px | 474 px | 프레임 이탈 시점 |

(중심부 기준. 어안이라 가장자리에서는 국소 배율이 작아 이동·크기가 더 줄어든다)

물체가 커지고 빨라져도 640 안에 들어온다. 카메라가 통 입구 가장자리에 있어
**z ≈ 0.11 m에서 물체가 프레임을 벗어나지만**, 그 시점이면 예측이 이미 수렴한 뒤라
칼만필터가 외삽한다 ([physics.md 6장](physics.md#카메라를-입구에-두는-대가--오프셋)).

**ROI를 놓쳤을 때:** 크롭 안에서 검출이 없으면 다음 프레임은 전체 프레임 탐색으로 되돌린다.
칼만필터는 유지한 채로 재획득한다.

## 3. 데이터셋 수집

### 왜 커스텀 학습이 필요한가

COCO 사전학습 모델에도 `bottle`, `cup`이 있지만 쓸 수 없다.

- **시점이 다르다.** 우리는 **아래에서 위를 본다.** COCO는 대부분 눈높이 측면 촬영이다
- **배경이 천장이다.** 형광등, 파이프, 천장 타일 — COCO에 거의 없는 배경
- **자세가 임의다.** 낙하 중 회전하며 떨어진다
- **모션 블러가 있다.** 6 m/s로 움직이는 물체 (글로벌 셔터라 왜곡은 없지만 블러는 남는다)
- **클래스 정의가 다르다.** 우리는 종류 무관하게 `trash` 하나로 잡아야 한다

### 촬영 조건

**실제 추론 조건과 같아야 한다.** 이게 원칙이다.

- 카메라를 **실제 장착 위치**(통 입구 림, 수직 상방)에 두고 촬영
- **실제 낙하 영상**을 찍어 프레임을 추출하는 것이 가장 효율적
  - 1초 영상 @ 60 fps = 60장
  - 노출·조명도 실제 설정 그대로 (0.84 ms, LED/스트로브 포함)
- 정지 물체도 일부 촬영 — **거리별로 찍어두면 z 추정 검증에 그대로 쓸 수 있다**

### 다양성 축

연속 프레임은 서로 거의 같아서 장수만 늘어나고 실질 다양성이 안 늘어난다.
**투척 횟수를 늘리는 것이 프레임을 더 뽑는 것보다 중요하다.**

| 축 | 범위 |
|---|---|
| 거리 z | 0.3 ~ 2.5 m (낙하 전 구간이 자연히 커버) |
| 자세 | 세로/가로/기울어짐 — 회전하며 떨어지므로 자연히 확보 |
| 배경 | 천장 3~5종 (강의실, 복도, 실험실 등) |
| 조명 | 형광등 / LED 보조광 / 혼합 |
| 물체 개체 | 3~5종 (캔·페트병·종이컵 등, 모두 `trash`로 라벨) |

### 목표 수량

| 항목 | 수량 |
|---|---|
| 투척 영상 | **100회 이상** |
| 회당 추출 프레임 | 10~15장 (낙하 구간 균등 샘플) |
| 낙하 프레임 합계 | 1000 ~ 1500장 |
| 정지 물체 (거리별) | 300장 |
| **합계** | **1300 ~ 1800장** |

### ⚠ 분할은 프레임이 아니라 **영상 단위**로

같은 영상에서 뽑은 프레임은 서로 거의 동일하다. 프레임 단위로 무작위 분할하면 train과 val에
사실상 같은 이미지가 들어가 **검증 점수가 부풀려지고 과적합을 못 잡는다.**

```
train / val / test = 70 / 20 / 10   ← 영상(투척 회차) 단위로 분할
test는 가능하면 별도 촬영 세션으로 확보
```

## 4. 라벨링

### 도구와 형식

- 도구: Roboflow / CVAT / LabelImg 중 택1
- 형식: **YOLO txt** — `class_id cx cy w h` (0~1 정규화)
- 클래스: `0 trash` (1개)

### ⚠ 라벨 품질이 곧 궤적 정확도다

이제 중요한 건 폭이 아니라 **중심**이다. 라벨이 한쪽으로 치우치면 중심이 밀리고,
그게 그대로 궤적 피팅의 관측 오차가 된다.

규칙:

1. **물체 외곽에 타이트하게.** 여백을 두면 중심이 밀린다
2. **모션 블러 처리를 일관되게.** 블러 꼬리를 포함할지 말지 정하고 **끝까지 같은 기준**을
   적용한다. 특히 **꼬리를 한쪽만 포함하면 중심이 치우친다** — 낙하 물체는 블러가
   진행 방향으로 생기므로 이 편향이 궤적을 따라 계통적으로 쌓인다
3. **가려짐(occlusion)이 있으면 제외.** 반쯤 가려진 프레임은 중심이 물체 중심이 아니다
4. **여러 명이 라벨링하면 먼저 기준을 맞춘다.** 같은 이미지 20장을 각자 라벨링해서
   **중심 좌표** 차이를 비교한다

> **폭 오차와 중심 오차는 성질이 다르다.** 폭 오차는 이제 무해하지만, 중심 오차는
> 재투영 잔차로 곧장 나타난다. 다만 중심 오차는 여러 프레임에 걸쳐 **평균화되어 눌리므로**
> 무작위 산포보다 **한쪽으로 쏠린 편향**이 훨씬 나쁘다.

## 5. 학습 (YOLOv8n)

구현: [`../pi5/prep/train_yolo.py`](../pi5/prep/train_yolo.py)

### 왜 YOLOv8n인가

- **n(nano)**: Hailo-8L에서 60 fps를 노려볼 수 있다. 프레임 예산이 16.7 ms이고 추론은
  10 ms 이내여야 한다 ([physics.md 7.4장](physics.md#74-프레임레이트와-처리-예산))
- **Hailo Model Zoo 지원이 확실하다.** yolo11n은 지원 여부가 미확인 리스크였는데
  ([open-questions.md](open-questions.md)), v8n을 쓰면 6장의 컴파일 단계에서 막힐 일이 없다
- 클래스 1개(`trash`), 물체가 단순해서 큰 모델이 필요 없다
- 정확한 bbox **중심**이 목표인데, 이건 모델 크기보다 **데이터 품질**에 더 좌우된다

> 정확도 차이는 이 용도에서 미미하다. 병목은 모델 크기가 아니라 라벨 품질이다.
> 나중에 바꾸고 싶으면 `train_yolo.py --model yolo11n.pt` 한 줄이면 된다
> (ultralytics가 동일하게 처리한다).

### 설정

```yaml
# dataset.yaml
path: ./dataset
train: images/train
val: images/val
names:
  0: trash
```

```python
from ultralytics import YOLO
model = YOLO("yolov8n.pt")          # COCO 사전학습 가중치에서 시작
model.train(
    data="dataset.yaml",
    imgsz=640,                       # ROI 크롭 크기와 일치시킨다 (2장)
    epochs=100,
    batch=16,
    patience=20,
)
```

**`imgsz=640`을 ROI 크롭 크기와 일치시키는 것이 중요하다.** 학습 때 본 물체 크기 분포와
추론 때 들어오는 분포가 같아야 bbox 회귀가 정확하다.

### 증강 주의사항

기본 증강은 대체로 도움이 되지만 두 가지는 조정한다.

- **좌우/상하 반전은 안전하다** (물체가 대칭이고 방향 의미가 없다)
- **scale 증강은 이제 넉넉히 줘도 된다.** 예전엔 bbox 크기가 곧 거리라 분포를 좁게
  유지했지만, 크기를 안 쓰게 되면서 그 제약이 풀렸다. 오히려 다양한 크기에서 중심을
  잘 잡는 게 중요하므로 실제 z 범위(0.3~2.5 m)를 넉넉히 덮는 편이 낫다
- **mosaic은 마지막 10 에폭에서 끈다** (`close_mosaic=10`, 기본값). 실제 추론에는
  모자이크가 없으므로 마무리는 실제 분포로 한다

## 6. Hailo 컴파일

```
yolov8n.pt  ──export──▶  ONNX  ──Hailo DFC──▶  .hef
                                  │
                          INT8 양자화 + calibration
```

### 절차

1. **ONNX 내보내기** — `model.export(format="onnx", imgsz=640, opset=...)`
2. **Hailo Dataflow Compiler**로 파싱 → 최적화 → 컴파일
3. **INT8 양자화 캘리브레이션** — 학습 데이터에서 **수백 장**을 캘리브레이션 세트로 제공.
   실제 추론 분포와 같아야 하므로 **ROI 크롭 이미지를 쓴다**
4. `.hef` 산출 → `config.YOLO_MODEL_PATH`에 경로 지정

### ⚠ 확인이 필요한 것

- **Hailo Model Zoo에서 yolov8n 레시피를 확인한다.** v8n을 고른 이유가 이것이지만,
  설치된 DFC 버전에서 실제로 도는지는 컴파일해봐야 안다
- **INT8 양자화가 bbox 정밀도를 떨어뜨릴 수 있다.** 양자화 전후로 **재투영 잔차**를
  비교해서 열화 폭을 반드시 측정한다. 이게 이 단계의 핵심 검증 항목이다

## 7. 검증 지표

**mAP만 보면 안 된다.** 이 시스템에 필요한 지표는 따로 있다.

| 지표 | 목표 | 측정 방법 |
|---|---|---|
| **재투영 잔차 (residual_px)** | **≤ 4 px** | `trajectory.Fit.residual_px`. `config.MAX_RESIDUAL_PX` |
| **착지 예측 오차** | 통 반경 이내 | 실제로 던져서 예측 착지점 vs 실제 착지점 |
| 추론 지연 (60 fps 전 프레임) | ≤ 16.7 ms | 초과 시 30 fps 격프레임 ([physics.md 7.4장](physics.md#74-프레임레이트와-처리-예산)) |
| 검출률 (recall) | ≥ 95% | 낙하 test 영상의 프레임별 |

**재투영 잔차가 새 합격 기준이다.** 추정한 궤적을 다시 화면에 투영해 실제 관측과 몇 px
어긋나는지를 본다. 이 하나에 **검출 노이즈 + 렌즈 왜곡 + 모델 오차**가 모두 합쳐져
들어오기 때문에, 무엇이 틀렸든 여기서 드러난다.

- 2 px 근처면 좋다
- 4 px을 넘으면 그 트랙은 버려진다 (`MAX_RESIDUAL_PX`)
- 계속 크면 `MIN_TIME_SPAN_S`를 늘려 관측 구간을 넓힌다

### ⚠ 잔차가 못 잡는 것 — 투영 모델 오류

**잔차는 "일관성"을 재지 "정확성"을 재지 않는다.** 투영 모델 자체가 틀리면 관측은
여전히 자기들끼리 일관되므로 **잔차가 작은 채로 답만 틀린다.**

어안 렌즈를 보정 없이 핀홀 해법에 넣었을 때를 측정했다 (2 m 낙하, 60 fps):

| 투척 오프셋 | 최대 입사각 | 착지 예측 오차 | 재투영 잔차 |
|---|---|---|---|
| 0.2 m | 6° | 0.0 cm | 0.00 px |
| 0.5 m | 44° | 2.1 cm | 1.19 px |
| 0.8 m | 62° | **10.4 cm** | 2.49 px |
| 1.2 m | 72° | **37.7 cm** | 2.72 px |
| 2.0 m | 80° | **158.7 cm** | **1.90 px** |

**158 cm를 틀렸는데 잔차는 1.90 px다.** `MAX_RESIDUAL_PX = 4.0`을 한 번도 넘지 않는다.
게이트가 통과시키므로 로봇은 **자신 있게 엉뚱한 곳으로 간다.** 오차가 커질수록 잔차가
오히려 줄어드는 구간까지 있다.

> 그래서 **렌즈 투영 모델은 잔차로 검증할 수 없다.** 캘리브레이션으로 직접 확인해야 한다
> ([`calibrate.py`](../pi5/prep/calibrate.py)가 실측 화각을 출력한다).
> 보정을 넣으면 위 표의 오차가 전부 **0.2 cm 이하**로 떨어진다
> ([`../pi5/fisheye.py`](../pi5/fisheye.py), [physics.md 7.2장](physics.md#72--이-렌즈는-핀홀이-아니다)).

잔차가 잡아주는 것은 **검출 노이즈, 오탐, 관측 부족**이다. 그건 여전히 유효하다.

### σ_w는 어떻게 됐나

`measure_sigma_w.py`는 남아 있지만 **합격 기준이 아니다.** bbox 폭 산포가 크면 검출
자체가 흔들린다는 신호이므로 **중심 좌표 품질의 간접 지표**로만 쓴다. 2 px 합격선은
이제 의미가 없다.

### 클래스

**`trash` 1개로 확정됐다** (2026-08-10). 실물 치수를 안 쓰게 되면서 종류를 구분할 이유가
사라졌다. 데이터 수집·라벨링 부담이 1/3이 되고 혼동 위험이 없어진다.

다만 **항력은 여전히 물체마다 다르다** — 종이컵은 100 g에서도 감속이 중력의 12%다
([physics.md 4장](physics.md#4-항력--포물선-모델이-양쪽-축에서-흔들린다)).
검출은 한 클래스로 묶되, **던지는 물체는 통제**하는 게 좋다.

## 8. 소프트웨어 인터페이스

[`../pi5/vision.py`](../pi5/vision.py)가 제공하는 계약이다.
아래 두 함수만 [main 루프](pi5-algorithm.md#4-메인-루프)가 쓴다.

> 실제 구현은 이 문서보다 더 줄었다 — 궤적 추정이 중심만 쓰게 되면서 `_estimate_z`와
> 속도 계산 블록이 삭제됐다. **`bbox`에서 실제로 소비되는 건 `cx, cy`뿐이다.**

```python
@dataclass
class Detection:
    class_name: str                            # 단일 클래스 "trash"
    bbox: tuple[float, float, float, float]   # cx, cy, w, h  (원본 1456×1088 픽셀 기준)
    confidence: float

def detect_full(frame) -> Detection | None:
    """전체 프레임 640 리사이즈 추론. 탐색 단계용."""

def detect_roi(frame, center_px: tuple[float, float]) -> Detection | None:
    """center_px 중심 640×640 네이티브 크롭 추론. 추적 단계용."""
```

**두 함수 모두 bbox를 원본 1456×1088 좌표계로 되돌려 반환한다.** ROI 오프셋과 리사이즈
스케일 역변환은 `vision.py` 안에서 끝내고, 바깥에서는 좌표계를 하나만 본다.

```
detect_full:  bbox_원본 = bbox_640 × (1456/640)
detect_roi :  bbox_원본 = bbox_640 + (roi_x0, roi_y0)      ← 스케일 없음
```

전처리(letterbox, 정규화)와 후처리(NMS)도 이 안에 둔다.
`main.py`는 `Detection`만 받는다.

## 9. 작업 순서

> **구현된 도구는 [`../pi5/prep/`](../pi5/prep/)에 있다.** 아래 각 단계에 대응하는 스크립트가 있고,
> 자동 라벨링은 MOG2 배경차분을 쓴다 — 카메라가 고정이고 배경(천장)이 정적이라 성립한다.

이 순서대로 하면 앞 단계 결과로 뒷 단계를 검증할 수 있다.

1. **카메라 캘리브레이션** — [`calibrate.py`](../pi5/prep/calibrate.py)로 `f_px`, 주점,
   왜곡계수 확보. **렌즈 초점거리도 여기서 확정된다**
   ([`../pi5/TODO.md`](../pi5/TODO.md) ★1번).
   실측 화각이 90°를 넘으면 `--model fisheye`로 다시 풀 것
   ([physics.md 7.2장](physics.md#72--이-렌즈는-핀홀이-아니다))
2. **정지 물체 촬영** — 거리별. 데이터셋 겸 검출 품질 기준 세트
3. **낙하 영상 촬영** — 100회 이상, 배경·조명 다양화
4. **프레임 추출 + 라벨링** — 라벨 기준 먼저 합의 (중심 기준)
5. **YOLOv8n 학습** — val에서 recall 확인
6. **재투영 잔차 측정** (양자화 전) — 실제 투척으로. **4 px을 못 맞추면 되돌아간다**
7. **Hailo 컴파일 + 양자화**
8. **재투영 잔차 재측정** (양자화 후) — 열화 폭 확인
9. **추론 지연 측정** — 10 ms 예산 검증
10. **ROI 추적 통합** — `detect_roi` 연결, 재획득 동작 확인

> 1번은 **데이터 수집을 막지 않는다.** `capture_dataset.py`는 초점거리를 쓰지 않으므로
> 병렬로 진행하면 된다.
