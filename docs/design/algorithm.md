# 동작 로직

물체가 화면에 들어온 순간부터 로봇이 받아내기까지, 파이5가 무엇을 어떻게 계산하는지.

관련 문서: [아키텍처](architecture.md) · [물리 계산](physics.md) ·
[비전 파이프라인](vision-pipeline.md) · [통신 프로토콜](protocol.md)

## 0. 근본 문제와 해결

사진 한 장은 **깊이를 담지 못한다.** 작은 물체가 가까이 있는 것과 큰 물체가 멀리 있는
것이 완전히 똑같은 픽셀을 만들기 때문이다.

**중력을 자로 쓴다.** 중력은 물체가 뭐든 항상 9.8 m/s²이므로, "이 궤적이 9.8의 중력으로
만들어지려면 거리가 얼마여야 하는가"를 역으로 풀면 스케일이 확정된다.
**물체 크기를 전혀 몰라도 되고**, bbox 중심만 쓰므로 물체가 공중에서 회전해도 무관하다.

## 1. 좌표계

```
카메라 원점, 광축(= 카메라가 보는 위쪽)이 +Z. X는 좌우, Y는 앞뒤.

        ● 물체
       ╱
      ╱  Z (광축, 위쪽)
     ╱   ↑
    ╱    │
   ●─────┼─────→ X
  카메라  │
        ↓ Y

착지 기준면 z_catch = CATCH_HEIGHT_M = −0.03 m = 통 입구 평면.
카메라가 통 입구보다 3 cm 위에 달려 있어서(실측), 받는 순간은 물체가 카메라가 아니라
입구 평면에 닿는 때다. 영향은 1 cm 미만이지만 항상 같은 방향이라 넣어둔다.
```

이미지 좌표 `(u, v)`는 u가 오른쪽, v가 **아래쪽**이 증가 방향이다.
`(cx, cy)`는 주점(principal point)으로, 캘리브레이션으로 구한다.

### body frame — 바퀴가 정의한다

로봇 좌표계는 바퀴 배치로 정의한다: **+Y = M1 방향(로봇 전방), +X = M1과 M2 사이로
나가는 방향(로봇 우측)**, 오른손 좌표계라 ω는 반시계가 +. 장착각은 M1 90° / M2 330° /
M3 210°다 ([`src/pi5/config.py`](../../src/pi5/config.py) `WHEEL_ANGLES_RAD`).

### 카메라 축 → body 축 회전 (`CAMERA_YAW_RAD`)

궤적은 **카메라 이미지 축**(X = 화면 오른쪽, Y = 화면 아래)으로 푼다. 오도메트리·역기구학은
**body 축**을 쓴다. 둘은 카메라를 몇 도 돌려 달았느냐만큼 어긋나 있고, 그 각도가
`config.CAMERA_YAW_RAD` 다. 카메라가 위를 보므로 두 좌표계는 같은 상방 축을 공유하는
오른손계라 **수평면 안의 순수 회전 하나**로 관계가 정해진다 — 거울 반전은 없다.

두 축이 만나는 곳은 `tracker.py` 두 군데뿐이다:

| 방향 | 함수 | 언제 |
|---|---|---|
| body → 카메라 | `Tracker._cam_xy()` → `robot_to_cam()` | 카메라 이동량을 피팅 입력으로 넣을 때 |
| 카메라 → body | `Tracker.landing()` → `cam_to_robot()` | 착지점을 내보낼 때 |

그래서 `tracker` 바깥(`control`, `main`)은 전부 body 축이고 `trajectory` 안은 전부 카메라
축이다. 각도는 `src/pi5/measure_camera_yaw.py` 로 잰다 — 사람이 4방향에 서서 찍은 사진의
방위각만 쓰므로 렌즈 왜곡·거리와 무관하고, 4방향 평균이 카메라 기울기 편향도 상쇄한다.

> ⚠ 현재 값 0.0 은 **사진 측정값(180°)이 아니라 실기에서 맞게 가는 값**이다. 사진은 카메라가
> 어디를 보는지만 재고 모터가 어느 쪽으로 도는지는 못 본다. 즉 모터 쪽에도 반전이 하나 더
> 있어서 서로 상쇄 중일 가능성이 크다 → [open-questions.md](open-questions.md)

### 카메라 오프셋 (`CAMERA_OFFSET_M`)

카메라가 통 입구 림에 튀어나오게 달려 광학 중심이 **회전 중심에서 전방 16 cm**(실측,
`(0.0, 0.16)`)다. 통 반경(13 cm)보다 커서 그대로 두면 매번 같은 방향으로 그만큼 어긋난다.
`Tracker._cam_xy()` 가 body 축에서 더한 뒤 카메라 축으로 돌린다. 이 덕에 착지점은 **트랙
시작 시점의 로봇 회전 중심** 기준으로 나온다.

## 2. 궤적 추정 (`src/pi5/trajectory.py`)

### 2-1. 미지수와 관측식

미지수는 t=0(첫 관측) 시점의 6개:

```
ρ = [X0, Vx, Y0, Vy, Z0, Vz]
```

운동 법칙:
```
X(t) = X0 + Vx·t                    (수평, 등속)
Y(t) = Y0 + Vy·t                    (수평, 등속)
Z(t) = Z0 + Vz·t − ½·g·t²           (수직, 등가속)
```

### 2-2. 왜 선형으로 풀리는가

핀홀 투영을 나눗셈(`u = fx·X/Z + cx`)이 아니라 **외적 잔차**로 쓰면 비선형성이 사라진다.
`a = u − cx`, `b = v − cy`로 두면:

```
a·Z(t) − fx·X(t) = 0
b·Z(t) − fy·Y(t) = 0
```

X, Y, Z가 미지수에 대해 1차이므로 위 두 식도 1차다. 이미 아는 중력항만 우변으로 넘어가
**비제차항**이 되는데, 바로 그것 때문에 해가 "한 배율만큼 자유로운 무한개"가 아니라
유일한 스케일을 갖는다.

프레임 `i`가 기여하는 행렬 두 행:
```
X-식:  [ −fx,  −fx·t,    0,     0,   a,  a·t ]   rhs = ½t²(fx·gx − a·gz)
Y-식:  [   0,      0,  −fy, −fy·t,   b,  b·t ]   rhs = ½t²(fy·gy − b·gz)
```

관측 하나당 식 2개이므로 **3관측이면 수학적으로 풀리고**, 그 이상은 최소제곱이 노이즈를
눌러준다. 반복도, 초기추정도, 수렴실패도 없다 — `np.linalg.lstsq` 한 번이면 끝난다.

> 실제로는 `MIN_OBSERVATIONS = 4`를 쓴다. 3이면 정방행렬이라 노이즈를 전혀 못 걸러낸다.

> `GRAVITY_CAM`을 회전시킨 값으로 바꾸면 **카메라를 기울여 달아도** 위 수식이 그대로
> 성립한다. 중력 방향이 상수로만 들어가기 때문이다.

### 2-3. 렌즈 왜곡 보정이 선행되어야 한다

**위 수식은 핀홀 투영을 전제한다.** 그런데 실제 렌즈는 대각 140° 어안(등입체각)이라
`r = f·tanθ`를 따르지 않는다. 보정 없이 넣으면 입사각 42°에서 깊이가 79%,
화면 끝에서 165% 틀린다.

그래서 `vision._undistort`가 검출된 **점 하나만** 핀홀 등가 좌표로 옮긴 뒤 피팅에
넣는다. 60 fps로 프레임 전체를 undistort하는 건 낭비다 — 프레임당 의미 있는 픽셀이
한 점뿐이다. 근거는 [`docs/design/physics.md` 7.2장](physics.md#72--이-렌즈는-핀홀이-아니다--등거리-어안이다).

## 3. 관측 시간 스팬 — 가장 중요한 파라미터

### 3-1. 왜 프레임 "개수"가 아니라 "시간"인가

궤적의 처짐량은 `⅛·g·T²`이라 **시간 스팬 T에 제곱**으로 붙는다. 반면 같은 시간에 프레임만
늘리면 노이즈 평균 효과로 `√N`밖에 못 얻는다. **시간을 벌리는 게 압도적으로 유리하다.**

### 3-2. 깊이는 아래에서 위로 수렴한다

관측값 자체(`a = u − cx`)가 행렬 계수에 들어가므로 픽셀 노이즈가 우변뿐 아니라 계수에도
섞인다(errors-in-variables). 그 결과 **깊이가 계통적으로 과소추정**되고, 스팬이 길어져야
서서히 참값으로 수렴한다.

깊이 추정비율(추정÷참값), 노이즈 1 px — 1.0이 정확:

| z0 | 0.30 s | 0.40 s | 0.50 s | 0.60 s | 0.70 s |
|---|---|---|---|---|---|
| 1.5 m | 0.35 | 0.75 | 0.94 | 0.99 | 1.00 |
| 2.5 m | 0.13 | 0.35 | 0.69 | 0.90 | 0.97 |
| 3.5 m | 0.07 | 0.16 | 0.37 | 0.67 | 0.86 |

**물체가 가까울수록 훨씬 빨리 수렴한다.** 카메라 배치는 "멀리서 보기"보다
"가까이서 오래 보기"가 낫다.

`MIN_TIME_SPAN_S = 0.40`은 **하한선**일 뿐이다. 그 전에는 계산 자체가 낭비라서 막아둔
것이고, 실제 수렴 판정은 아래 3-4가 한다.

### 3-3. 잔차는 깊이 정확도의 지표가 아니다 ★

재투영 잔차(`residual_px`)가 작다고 깊이가 맞는 게 아니다. **스케일이 틀린 궤적도 화면에는
잘 맞게 투영되기 때문이다** — 그게 단안 카메라의 원래 모호성이고, 중력이 그 모호성을
깨주지만 관측 시간이 짧으면 충분히 못 깬다.

> 실측: 스팬 0.5초에서 잔차 **1.58 px(아주 좋음)** 인데 깊이는 참값의 **69%** 였다.

잔차는 다른 역할을 한다 — 포물선으로 설명이 안 되는 궤적(사람 팔, 흔들리는 커튼,
검출 오탐)을 걸러내는 **탄도 게이트**다 (`MAX_RESIDUAL_PX = 4.0`).

> **⚠ 잔차를 만능으로 믿지 말 것.** 검출 노이즈·오탐·관측 부족은 잘 잡지만
> **투영 모델 오류는 못 잡는다.** 관측이 자기들끼리 일관되기만 하면 잔차는 작게 나온다.

### 3-4. 깊이 수렴 판정 (`Tracker._depth_converged`)

```
전체 관측으로 푼 깊이  vs  앞쪽 70% 관측만으로 푼 깊이
                     ↓
        두 값이 2배 이내로 가까우면 수렴한 것으로 본다
```

깊이는 스팬이 짧을수록 작게 나오는 계통 편향이 있으므로, 두 추정이 가까워졌다는 건 곧
수렴했다는 뜻이다. **노이즈 크기를 미리 몰라도 되는 자기 교정식 판정**이라 이 방식을 택했다.

> 이 값을 조이면 정확해지지만 **예측이 너무 늦게 나온다.** `ratio = 1.15`로 조였을 때는
> 예측이 착지 0.08초 전에야 나와서 로봇이 움직일 시간이 없었다(성공률 23%).
> 현재 `DEPTH_STABILITY_RATIO = 2.0`.

### 3-5. 편향 방향이 안전하다

오차가 **항상 과소추정** 방향이다. 즉 로봇이 목표보다 **덜 간다.** 아래에서 위로 수렴하지
절대 오버슈트하지 않는다. 덜 간 만큼은 다음 사이클이 이어서 가면 된다.
반대(과대추정)였다면 위험했을 것이다.

## 4. 착지 예측

```
Z(t) = z_catch 를 만족하는 t 중 **나중 근**
X_land = X0 + Vx · t_land
Y_land = Y0 + Vy · t_land
```

**나중 근을 쓰는 이유:** 위로 던져 올린 궤적은 캐치 평면을 두 번 지난다(올라갈 때, 내려올 때).
받아야 하는 건 내려올 때다.

판별식이 음수면 정점이 캐치 평면보다 낮다는 뜻 → 도달 못 함 → `None`을 돌려주고 명령을
내지 않는다.

## 5. 제어 루프 (`src/pi5/main.py`, `control.py`)

```
매 프레임:
  ① 캡처 → YOLO → 검출 후보 전체 (u, v, t)              [vision.observe]
  ② 오도메트리 수신 (논블로킹, 최신 하나)                 [communication.try_receive_odometry]
  ③ 후보마다 가설 갱신 → 물리 통과분 채택 → 착지 예측      [TrackerPool.step]
  ④ 명령 — 아래 셋 중 하나
       a. 채택된 궤적이 있다                 → 착지점(거리 하한) → 월드 좌표 목표점   5-1, 5-3
       b. 궤적은 없는데 직전 목표가 살아 있다 → coast: 그 목표를 계속 보낸다         5-4
       c. 둘 다 없는데 빠르게 나는 후보가 있다 → 조기 출발: 화면 이동방향으로       5-2
  ⑤ 사이클 종료 판단 → 리셋 (coast 중이면 정지 명령을 보내지 않는다)               5-5
```

**매 프레임 처음부터 다시 피팅한다.** 이 규모에선 최소제곱이 0.06 ms라 아낄 게 없고(후보 8개를
동시에 돌려도 프레임당 0.13 ms), 배치 피팅은 물리를 매 프레임 정확히 강제한다.

**설계 기조는 "정확한 예측을 기다리지 말고 먼저 움직인다" 이다.** 실기(60 fps)에서 완전한
궤적 fit이 나오기까지 16~17프레임(0.27초)이 걸렸는데, 물체는 첫 검출 후 0.10~0.13초면 이미
카메라 머리 위를 지나간다. 연산이 느린 게 아니라 **판단할 관측이 모일 때까지 기다리는 시간**이
문제였다. 5-2 ~ 5-4는 전부 그 대기를 우회하는 장치다.

### 5-1. 남은거리 ÷ 남은시간 (계산 주체는 피코)

```
남은거리 0.50 m / 남은시간 0.50 s → 1.00 m/s
남은거리 0.20 m / 남은시간 0.25 s → 0.80 m/s
남은거리 0.03 m / 남은시간 0.10 s → 0.30 m/s
```

목표에 가까워질수록 목표속도가 저절로 줄어 **별도 감속 프로파일 없이 감속기 역할**을 한다.
남은 거리는 **목표점 − 피코 자신의 pose**다. 파이는 월드 좌표 도착 지점만 보내고 뺄셈에
관여하지 않는다 — 미리 빼서 보내면 피코가 또 빼서 두 번 빠진다.

**단, 남은시간을 `DRIVE_AGGRESSION`(8.0)으로 나눠서 보낸다.** 그대로 보내면 시간이 넉넉한
초반에 일부러 느리게 간다(0.3 m를 0.5초 안에 가면 되니 0.6 m/s). 그런데 예측 목표점은 깊이가
과소추정에서 참값으로 올라오며 **시간이 갈수록 멀어지므로**, 초반에 여유를 부리면 못
따라잡는다. 8로 나누면 사실상 "항상 최고속도"이고 감속은 목표 약 5 cm 앞에서야 시작된다
(1.0 → 37 cm 앞, 2.0 → 18 cm, 4.0 → 9 cm).

상한은 **방향별 바퀴 속도 기준**이고, 넘으면 **크기만 깎고 방향은 보존**한다
([pico-control.md 3장](pico-control.md#3-기구학)). 도착 허용오차(`POSITION_TOLERANCE_M`,
2 cm) 안이면 정지한다.

### 5-2. 조기 출발 — 방향은 3프레임이면 안다

카메라가 하늘을 보므로 **화면상 위치가 곧 방위각**이고, 그건 깊이와 무관하게 정확하다.
그래서 fit이 없어도 물체가 화면에서 흘러가는 방향만 보면 어느 쪽으로 갈지는 안다. 거리만
모른다. 거리는 모르는 대로 `EARLY_START_DIST_M`(1.0 m) 앞을 목표로 줘서 일단 최고속도로
가속하고, 진짜 fit이 나오는 순간 목표를 갈아탄다 — 그 사이 모터 가속 지연을 미리 먹어치운다.

- **현재 위치가 아니라 이동 방향**(첫 관측 → 마지막 관측)을 쓴다. 물체는 반대편 하늘에서
  머리 위를 지나 착지점으로 넘어가므로, 초반의 현재 방위각은 오히려 정반대를 가리킨다
- 판정은 **화면 이동속도 ≥ `EARLY_START_MIN_PX_PER_S`(350 px/s)** 하나다. 누적 이동량
  (40 px)으로 보면 물체가 먼 초반에 6프레임을 기다려야 했는데, 속도로 보면 3프레임에 갈린다
  (시뮬, 60 fps·노이즈 1.5 px: 실제 투척 406~773 px/s, 정지 오탐 56~302 px/s)
- 결과: 첫 명령이 **17프레임(0.267 s) → 3프레임(0.05 s)**, 정지 오탐 발동률 0% (시뮬)

### 5-3. 목표 거리 하한 — 방향은 믿고 거리에 바닥을 깐다

초반 fit의 깊이는 참값의 15~25%라 착지점이 "16 cm 앞"처럼 나온다. 그러면 로봇이 16 cm 가고
도착 판정에 걸려 **정상적으로 선다** — 실제 착지는 훨씬 멀다. 방향은 정확하므로, 착지점이
`MIN_TARGET_DIST_M`(0.6 m)보다 가까우면 **같은 방향으로 거리만 늘려서** 보낸다. 깊이가 참값에
붙으면 착지점이 이 값을 자연히 넘어가고 그때부터는 손대지 않는다.

기준점은 **트랙 시작 시점의 로봇 위치**다. "현재 위치에서 최소 X m"로 하면 로봇이 갈수록
목표도 밀려나 영원히 못 잡는다. ⚠ 실제 착지가 0.6 m 안이면 그만큼 지나친다. 0이면 꺼진다.

### 5-4. coast — 물체를 놓쳐도 목표까지 간다

던져진 물체는 탄도라 **안 보인다고 궤적이 바뀌지 않는다.** 그리고 물체는 거의 항상 착지
직전에 화면을 벗어난다 — 카메라 쪽으로 떨어지니 `u = fx·X/Z` 가 Z→0에서 발산하고, 가까워질수록
블러로 검출도 끊긴다. 즉 **로봇이 제일 움직여야 할 순간에 시야를 잃는다.** 두 층으로 막는다:

| 층 | 어디서 | 하는 일 |
|---|---|---|
| 트랙 | `TrackerPool.cycle_end_reason` | **fit이 있는 트랙은 유실로 사이클을 끝내지 않는다.** 남은시간은 `landing(now)` 로 실제 시각 기준으로 계속 줄어든다(마지막 관측 시각 기준이면 얼어붙어서 피코가 여유 있다고 착각한다) |
| 구동 | `main.py` coast 분기 | 사이클이 끝나 pool이 리셋돼도 **마지막 목표점을 계속 보낸다.** 피코 pose가 목표 2 cm 안이면 정지, `착지 예정시각 + COAST_EXTRA_S(0.5 s)` 를 넘기면 포기 |

또 `Tracker.add()` 는 한 프레임 게이트를 못 넘겨도 직전 fit을 `FIT_HOLD_S`(0.15 s)까지 들고
간다 — 깊이 수렴 판정이 노이즈로 한 프레임만 흔들려도 명령이 끊기던 문제.

### 5-5. 사이클 종료와 리셋

| 사유 | 조건 | 비고 |
|---|---|---|
| 착지 시각 경과 | 채택 궤적의 `landing(now)` 남은시간 ≤ 0 | 이후 coast 가 이어받는다 |
| 물체 유실 | 채택 트랙에 **fit이 없고** `TRACK_MAX_GAP_S`(0.15 s) 넘게 못 봄 | fit 있는 트랙은 여기 안 걸린다 |
| 사이클 타임아웃 | 채택 후 `CYCLE_TIMEOUT_S`(2.0 s) | |
| **미채택 타임아웃** | 채택된 궤적 없이 가설이 생긴 지 2.0 s | 천장 오탐만 붙잡고 있는 상태를 끊는다. 없으면 오탐 가설이 무한정 살아 관측을 쌓는다 — 로봇 주행 중 오탐 채택이 리셋 있을 때보다 4~7배 많았다(시뮬) |

리셋 뒤 `COOLDOWN_S`(0.8 s)는 **명령을 실제로 보낸 사이클에만** 둔다 — 가만히 있었으면 쉴
이유가 없고, 쉬는 동안 날아오는 걸 놓칠 뿐이다.

### 5-6. 이 설계가 치르는 대가 (알고 쓸 것)

- **오버슈트가 늘었다.** 전속으로 붙고 거리에 하한을 깔았으니 당연하다. 정지거리는 아직 안
  쟀다 ([pico/TODO.md](../../src/pico/TODO.md))
- **조기 출발은 움직이는 오탐도 탄다.** 350 px/s를 넘는 것(사람 손, 흔들리는 물체)이면
  로봇이 그쪽으로 튄다
- **로봇이 움직이면 정지한 천장점도 궤적으로 채택될 수 있다.** 시차로 화면에서 곡선을 그려서다.
  시뮬 채택률: 0 m/s 0%, 0.25 m/s 10.5%, 0.5 m/s 47.5%, 1.4 m/s 57%. 기존 게이트를 전부
  통과하지만 **잔차 분포로는 갈린다**(오탐 중앙값 11.2 px vs 실제 투척 1.4 px).
  `MAX_RESIDUAL_PX` 6.0 → 3.0이면 오탐 통과 23.6% → 7.1%, 진짜 통과 98.8% → 91.2%.
  실기 잔차를 보고 정하려고 아직 안 바꿨다
- 비교용 `main.py --no-gates` — "진짜인지" 따지는 게이트(이동량·잔차·속도상한·조건수·수렴검사)를
  끄고 스팬 하한을 0.10 s로 내린다. `MIN_TIME_SPAN_S` 와 `Z_RANGE_M` 은 **안 끈다** — 둘까지
  끄면 관측 4개짜리 fit(깊이 15%)이 조기 출발의 올바른 방향을 "16 cm 앞"으로 덮어써서 로봇이
  한 틱 가고 선다

## 6. 검증된 성능

실제 카메라 스펙(GS 카메라, f=1739px, 1456×1088 @60fps, 화각 45°×35°)으로 합성 투척
150회, 중앙값. "이동가능"은 첫 예측 시점부터 착지까지 남은 시간:

| z0 | 노이즈 | 비행 | 화면체류 | 프레임 | 첫예측 | 이동가능 | 첫오차 | 최종오차 | 성공률 |
|---|---|---|---|---|---|---|---|---|---|
| 1.5 m | 1.0 px | 0.73 s | 0.67 s | 41 | 0.47 s | **0.26 s** | 2.2 cm | 0.1 cm | 100% |
| 2.0 m | 1.0 px | 0.81 s | 0.75 s | 46 | 0.53 s | **0.28 s** | 2.9 cm | 0.2 cm | 100% |
| 2.5 m | 0.5 px | 0.88 s | 0.82 s | 50 | 0.48 s | **0.40 s** | 4.3 cm | 0.1 cm | 100% |
| 2.5 m | 1.0 px | 0.88 s | 0.82 s | 50 | 0.62 s | **0.27 s** | 2.9 cm | 0.4 cm | 100% |
| 2.5 m | 2.0 px | 0.88 s | 0.82 s | 50 | 0.78 s | 0.10 s | 2.2 cm | 1.5 cm | 30% |
| 3.0 m | 1.0 px | 0.95 s | 0.87 s | 53 | 0.65 s | **0.30 s** | 3.6 cm | 1.0 cm | 99% |

**검출 노이즈 1px 이하가 목표다.** 2px면 예측이 착지 직전에야 나와서 로봇이 못 움직인다.
0.5px면 0.40초를 벌어준다. 모션 블러 억제(짧은 노출 + 높은 게인)가 그대로 예측 성능으로
돌아온다 — 글로벌 셔터 + 큰 픽셀(3.45µm)이 여기서 값을 한다.

> **⚠ 이 표는 f_px = 1739(6 mm 렌즈, 화각 45°×35°) 기준으로 돌린 것이다.**
> 실측 렌즈는 번들 M12 어안으로 **f_px 973** (2026-08-19 캘리브레이션)이라, 같은 1 px
> 노이즈가 약 1.8배 큰 각도 오차에 해당한다. 화각이 넓어져 화면 체류 시간이 늘어나는
> 이득도 함께 있으므로 단순 악화는 아니지만, **실측 스펙으로 다시 돌려봐야 한다.**
> → [`docs/design/open-questions.md`](open-questions.md)

## 7. 물체 인식의 역할 (`src/pi5/vision.py`)

궤적 추정이 물체 크기를 안 쓰므로 YOLO가 할 일이 작다.

| 항목 | 내용 |
|---|---|
| 클래스 | **1개 (`trash`)** — 종류를 구분해도 쓸 데가 없다 |
| 쓰는 값 | bbox **중심**(u, v) |
| 안 쓰는 값 | bbox 크기 (로그·디버깅용으로만 남긴다) |
| 합격 기준 | **중심 좌표 노이즈 ≤ 1 px** |
| 물체 회전 | 중심은 불변 — 무관 |

여러 개가 잡히면 가장 신뢰도 높은 것 하나만 쓴다. 한 번에 하나만 던진다는 전제이고,
오탐이 섞여도 3-3의 탄도 게이트에서 걸러진다.

학습 데이터 수집·라벨링·Hailo 변환은 [`docs/design/vision-pipeline.md`](vision-pipeline.md).

## 8. 파라미터

전부 [`src/pi5/config.py`](../../src/pi5/config.py)에 있고, **각 값에 근거가 주석으로 붙어 있다.**
실행 중 바꾸려면 `python main.py --set 이름=값` (여러 번 가능).

| 이름 | 값 | 역할 |
|---|---|---|
| `MIN_OBSERVATIONS` | 4 | fit 최소 관측 수 (3이면 정방행렬이라 노이즈를 못 거른다) |
| `MIN_TIME_SPAN_S` | 0.2 | fit 최소 관측 스팬. **첫 명령 지연의 주범** — 5-2로 우회 |
| `MAX_RESIDUAL_PX` | 6.0 | 탄도 게이트 (잔차 ≠ 깊이 정확도, 3-3) |
| `MIN_TRACK_DISPLACEMENT_PX` | 40 | 정지 오탐 사전 차단 (누적 이동량) |
| `MAX_LAUNCH_SPEED_MPS` | 10.0 | 풀린 초기속도 상한 |
| `Z_RANGE_M` | 0.15 ~ 6.0 | 깊이 발산 차단 |
| `DEPTH_STABILITY_RATIO` | 2.0 | 깊이 수렴 판정 (첫 fit은 면제) |
| `FIT_HOLD_S` | 0.15 | 게이트 실패 시 직전 fit 유지 |
| `ASSOC_STEP_PX` | 150 | 검출 ↔ 가설 연관 반경 |
| `TRACK_MAX_GAP_S` | 0.15 | fit 없는 트랙의 유실 판정 |
| `CYCLE_TIMEOUT_S` / `COOLDOWN_S` | 2.0 / 0.8 | 사이클 상한 / 명령 보낸 뒤 휴지 |
| `EARLY_START_OBS` / `EARLY_START_MIN_PX_PER_S` / `EARLY_START_DIST_M` | 3 / 350 / 1.0 | 조기 출발 (5-2) |
| `MIN_TARGET_DIST_M` | 0.6 | 목표 거리 하한 (5-3) |
| `DRIVE_AGGRESSION` | 8.0 | 남은시간 나눔 = 초반 속도 (5-1) |
| `COAST_EXTRA_S` | 0.5 | 착지시각 이후 coast 여유 (5-4) |
| `DRIVE_TIMEOUT_S` | 0.15 | 피코 워치독 |
| `CAMERA_YAW_RAD` / `CAMERA_OFFSET_M` / `CATCH_HEIGHT_M` | 0.0 / (0, 0.16) / −0.03 | 장착 실측 (1장) |

**렌즈 왜곡 보정은 검출된 점 하나만** 한다 (`vision._undistort` → `fisheye.to_pinhole_px`).
프레임 전체를 펴는 건 낭비다 — 프레임당 의미 있는 픽셀이 한 점뿐이다.
