# 피코 — 모터 실시간 제어

피코가 하는 일은 하나다. **파이5가 준 목표 속도를 정확히 낸다.**
어디로 가야 하는지, 물체가 어디 떨어지는지는 [파이5](../algorithm.md)가 판단한다.

**피코는 궤적도 착지점도 모른다.** 이 경계를 지키는 것이 설계의 핵심이다.

관련 문서: [하드웨어](hardware.md) · [통신 프로토콜](protocol.md) · [물리 계산](physics.md)

---

## 1. 왜 별도 MCU인가

리눅스는 실시간 OS가 아니라 1 kHz PID 루프의 주기를 보장할 수 없다. 스케줄러 지터가 수 ms
단위로 튄다. PID의 미분항은 `de/dt`를 쓰기 때문에 dt가 흔들리면 출력이 요동친다.

피코는 인터럽트 없는 슈퍼루프로 1 ms 주기를 정확히 지키고, PIO 하드웨어로 엔코더를 CPU
개입 없이 카운트한다.

---

## 2. 1 kHz 제어 루프

```
매 1 ms:
  1. 엔코더 카운트 읽기            (PIO, 하드웨어 누적)
  2. 카운트 차분 → 바퀴 선속도 3개
  3. 순기구학 → body 속도 (vx, vy, omega)
  4. 1D 칼만 스무딩 → world 회전 → 위치 적분 (오도메트리)
  5. 파이5 명령 수신 확인 (non-blocking) / TTL 감소, 만료 시 정지
  6. 역기구학: 목표 body 속도 → 바퀴 3개 목표 속도
  7. 바퀴별 피드포워드 + PID → PWM 듀티
  8. (10 사이클마다) 오도메트리 송신 — 버퍼 여유 있을 때만
```

주기 유지는 `sleep_until(next_tick)` 방식을 쓴다. `sleep_ms(1)`을 쓰면 루프 처리시간이
누적되어 주기가 밀린다.

**부팅 직후부터 계속 돈다.** 파이5가 아무것도 안 보냈어도 엔코더를 읽고 오도메트리를
갱신한다 (명령이 없으면 목표 속도 0, 정지 상태 유지).

## 3. 기구학

바퀴 장착각 `β_i`, 중심-바퀴 거리 `L`.

```
역기구학:  v_i = −sin(β_i)·vx + cos(β_i)·vy + L·ω
순기구학:  위 3×3 행렬의 역행렬 (여인수/수반행렬 공식)
```

장착각은 **M1 = 90°(전방, +Y) / M2 = 330°(우측 뒤) / M3 = 210°(좌측 뒤)**, L = 0.15 m다.
β_i는 중심에서 바퀴를 본 위치각이고 옴니 바퀴가 구르는 방향은 그 접선(β_i+90°)이라,
위 식의 앞 두 항이 곧 접선 단위벡터다. **등간격 오차는 조립 후 실측** — 1~2° 틀어지면
직진 명령에 로봇이 비스듬히 간다.

**구현 완료 및 실행 검증됨** ([`kinematics.c`](../pico/kinematics.c), 2026-07-31).
단위 테스트로 `forward(inverse(v)) == v`를 강제한다.

## 4. 오도메트리

순기구학 결과에는 엔코더 양자화 노이즈가 낀다. 축(vx, vy, omega)별 **독립 1D 칼만필터**로
스무딩한 뒤 적분한다. 상태는 속도 자체이며 가속도 모델은 없다 — 노이즈 제거가 목적이다.

```
body 속도를 로봇 방향(theta)으로 회전시켜 world frame으로 바꾼 뒤 적분:

  x     += (vx·cosθ − vy·sinθ) · dt
  y     += (vx·sinθ + vy·cosθ) · dt
  theta += ω · dt
```

이 `(x, y, theta)`가 트랙 시작 시점 기준의 누적 이동량이고, 파이5는 착지점에서 이 값을
빼서 **남은 거리**를 구한다 ([../algorithm.md 5-1장](../algorithm.md#5-1-목표-속도--남은거리--남은시간)).

**⚠ 옴니휠은 슬립이 있다.** 롤러가 측면으로 구르는 구조라 마찰이 작고, 엔코더가 본 회전이
실제 이동과 어긋난다. 캐치 사이클이 1초 이내로 짧아서 누적은 제한적이지만, 가속 구간의
슬립은 이동거리를 **과대평가**하는 방향이라 슬루레이트 제한으로 애초에 막는다 (5절).

## 5. 모터 제어 — 피드포워드 + PID

순수 PID만 쓰면 PID 출력(속도 오차 단위)을 PWM 듀티(0~1)로 바꿀 스케일 계수를 따로
정해야 하는데, 피드포워드를 넣으면 그 문제가 구조적으로 사라진다:

```c
duty_ff = v_target / V_WHEEL_MAX;           // 개루프 근사 (전압 ∝ 무부하 속도)
duty_fb = kp*e + ki*∫e + kd*de/dt;          // 오차 보정만 담당
duty    = clamp(duty_ff + duty_fb, -1, +1);
```

피드포워드가 대부분의 일을 하므로 PID는 작은 보정만 하면 된다. **게인 튜닝이 훨씬 쉬워지고
응답도 빨라진다.** 순수 PID는 오차가 생겨야만 출력이 나오므로 구조적으로 한 박자 늦다.

### 함께 필요한 것

| 항목 | 이유 |
|---|---|
| **적분 와인드업 클램프** | 듀티가 포화된 동안 적분을 멈추거나 클램프하지 않으면 `integral`이 무한정 커지고, 방향 전환 시 크게 오버슈트한다 |
| **데드밴드 보상** | 기어드 모터는 듀티 10~15% 이하에서 안 움직인다. 0이 아닌 목표에는 최소 듀티를 더해준다 |
| **DIAG 핀 확인** (선택) | BTS7960의 과전류·과열 플래그를 읽어 로그에 남긴다 |

### PWM 출력

BTS7960은 RPWM / LPWM 2채널 방식이다. 출력 부호에 따라 한쪽에만 PWM을 주고 다른 쪽은 0으로
둔다. EN 핀은 상시 HIGH.

```c
if (duty >= 0) { set_pwm(rpwm,  duty); set_pwm(lpwm, 0); }
else           { set_pwm(rpwm, 0);     set_pwm(lpwm, -duty); }
```

## 6. 엔코더 (PIO)

PIO로 **A상 상승엣지만 세고, 그 순간 B상 레벨로 방향을 판단**하는 1x 쿼드러처 디코딩이다.
CPU 개입 없이 하드웨어가 카운트를 누적하고, 상위 코드는 값만 읽는다.

- PIO에는 덧셈 명령이 없어서 증가는 `반전 → 감소 → 반전` 트릭을 쓴다
- **1x라서 4x 대비 분해능이 1/4이다.** `ENCODER_COUNTS_PER_REV`를 그에 맞게 넣어야 한다
- PIO FIFO가 차서 push가 버려져도 무해하다. X 레지스터에 **누적 절대값**이 들어 있고 최신
  값만 읽기 때문이다 — 잘 된 설계다
- 분해능이 부족하면 4x 디코딩으로 승급한다 (PIO 프로그램 교체)

**엔코더는 기어박스 이전(모터축)에 붙어 있다.** 바퀴 속도로 변환할 때 기어비 43.8로 나눈다:

```c
motor_revs = delta_counts / ENCODER_COUNTS_PER_REV;
wheel_revs = motor_revs / GEAR_RATIO;          // FIT0186: 43.8:1
speed      = wheel_revs * (WHEEL_DIAMETER_M * M_PI) / dt;
```

**FIT0186: 모터축 16 CPR, 기어비 43.8:1 → 출력축 700 CPR.**
데이터시트에 "64 CPR / 2797 CPR"도 같이 적혀 있는데 **4x 디코딩 기준 값**이다
(64 = 16×4, 2797 ≈ 700×4). 우리 PIO는 **1x 디코딩**이므로 **16을 쓴다.**

**⚠ 엔코더 VCC는 3.3 V에 물린다.** 엔코더가 3.3~5 V를 지원하고 출력은 VCC 기준으로
스윙하므로, 3.3 V로 급전하면 피코에 **직결해도 안전하다**. 5 V로 물리면 엔코더는 멀쩡한데
피코가 죽는다 ([hardware.md 3.2장](hardware.md#32-엔코더)).

현재 `encoder_pio.c`의 `gpio_pull_up()`은 **그대로 두면 된다** — 3.3 V 스윙이면
푸시풀이든 오픈드레인이든 안전하게 동작한다.

```
pico/
├── CMakeLists.txt          # 빌드 설정

├── motor_control.c/.h      # FF + PID + PWM (5절)
└── communication.c/.h      # 프레임 송수신 (protocol.md)
```

## 8. 파라미터

`pico/config.h`에 모은다.

### 배선 후 확정

| 값 | 방법 |
|---|---|
| `MOTOR_PINS[3]` | 모터당 rpwm / lpwm / en / enc_a / enc_b 5핀 ([hardware.md 7장](hardware.md#7-배선)) |
| 엔코더 풀업 | 내부 풀업 유지. VCC를 3.3 V에 물리는 것이 전제 ([hardware.md 3.2장](hardware.md#32-엔코더)) |

### 조립 후 실측

| 값 | 임시값 | 방법 |
|---|---|---|
| `ENCODER_COUNTS_PER_REV` | **16** (모터축, 1x 디코딩) | 데이터시트 확정. 1회전 실측으로 교차검증 |
| `GEAR_RATIO` | **43.8** (FIT0186) | 데이터시트 |
| `WHEEL_ANGLES_RAD[3]` | M1 90° / M2 330° / M3 210° | 배치 확정. 등간격 오차만 각도기 실측 + 주행 보정 |
| `WHEEL_MOUNT_RADIUS_M` | 0.15 m | 자 실측 + 회전 보정 |

### 구동 튜닝

| 값 | 임시값 | 방법 |
|---|---|---|
| `V_WHEEL_MAX` (FF 스케일) | 미정 | 듀티-속도 곡선 측정 |
| `MOTOR_DEADBAND_DUTY` | 미정 | 최소 구동 듀티 측정 |
| `MOTOR_PID[3]` | {1, 0, 0} ×3 | FF 먼저 → kp → kd → ki |
| `INTEGRAL_LIMIT` | 미정 | 와인드업 클램프 |
| `PROCESS_NOISE` / `MEASURE_NOISE` | 0.01 / 1.0 | 칼만 스무딩 정도 |
| `SLEW_RATE_LIMIT` | 2.45 m/s² (μ=0.5) | 슬립 방지 — μ 실측 후 확정 |

## 9. 브링업 절차

**순서대로 한다. 앞 단계가 안 되면 뒷 단계는 디버깅이 불가능하다.**

1. **빌드** — SDK 설치, `PICO_SDK_PATH` 설정, 블링크로 업로드 경로 확인
2. **엔코더 출력 방식 판별 + 단독 테스트** — 피코를 연결하기 **전에** 5 V만 주고
   멀티미터로 푸시풀/오픈드레인을 판별한다 ([hardware.md 3.2장](hardware.md#32-엔코더)).
   그 다음 손으로 1회전 → 카운트 16 확인, 역회전 시 부호 반전 확인
3. **모터 개루프** — 듀티를 0.1씩 올리며 바퀴 속도 측정
   → **듀티-속도 곡선** 작성 → `V_WHEEL_MAX`, `MOTOR_DEADBAND_DUTY` 확정
4. **속도 폐루프 (모터 1개)** — 피드포워드만으로 목표 속도 추종 확인 → kp 추가 → kd → ki
   → 스텝 응답에서 오버슈트·정착시간 확인
5. **3륜 합성** — "X 방향 1 m" 명령 → 실제 이동 측정 → `WHEEL_ANGLES_RAD`,
   `WHEEL_MOUNT_RADIUS_M` 보정. 대각 방향도 확인
6. **오도메트리 검증** — 사각형 주행 후 원점 복귀 오차 측정 → `σ_odom` 확정
7. **가속도 · 마찰계수 실측** — 정지에서 전속까지 엔코더 로그
   - 초기 구간의 기울기가 **견인 한계** `a = 0.5·μ·g`다 → 여기서 **μ를 역산**한다
   - 바퀴가 헛도는지 확인한다. 엔코더 속도는 오르는데 로봇이 안 나가면 슬립이다
     (실제 이동거리를 자로 재서 대조)
   - → **[physics.md 6장](physics.md#6-통-입구-크기--설계의-지렛대) 표에서 해당 μ 열을 읽으면
     유효 캐치 반경이 확정된다** (30 cm 통 기준: μ=0.4→41 cm, μ=0.5→48 cm, μ=0.7→56 cm)
   - 모터가 마찰 한계의 4배 토크를 낼 수 있으므로 **슬립이 실제로 일어난다.**
     슬루레이트 제한값도 여기서 정한다
8. **통신 왕복** — [protocol.md](protocol.md)의 프레임 테스트 통과
